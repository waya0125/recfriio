# Quixun QRS-UT100B（ASICEN ASV5211 + ASIE5606）

Quixun QRS-UT100B（地デジ・CATV）を Go 版の `recfriio --hdp`（`recut100b` と同じ）で使うときの説明と、中身を調べた結果です。  
共通の使い方とオプションは [README](../README.md) にあります。

## 1. 概要

| 項目 | 内容 |
|---|---|
| USB ID | `1738:5211`（ファームが無い状態）→ `3275:7020`（ファームを送ったあと） |
| 放送波 | 地デジ（UHF 13〜62ch）・CATV（C13〜C63ch） |
| チューナー数 | 1 |
| B-CAS | 本体のスロット（外付けのカードリーダーも可） |
| ファームウェア | 電源が入るたびに送る必要がある（付属 CD のローダーから取り出す） |
| Linux | [recfriio](../README.md)（`--hdp`） |
| Windows | [BonDriver_Friio](https://github.com/waya0125/BonDriver_Friio) |
| 公式ページ | メーカーのサイトはなくなっている。[製品ページ](http://web.archive.org/web/20100224054943/http://www.quixun.co.jp:80/product/qrs-ut100b.html)・[サポートページ](http://web.archive.org/web/20100212202729/http://www.quixun.co.jp:80/support/qrs-ut100b.html)（Wayback Machine） |

## 2. 準備

udev ルールは [README の「準備」](../README.md#準備) にあります。

UT100B は電源が入るたびに、ファームの無い状態（`1738:5211`）で起動します。  
ファームを送ると `3275:7020` として出直します。  
ファームはメーカーの著作物なので、このリポジトリには含めていません。  
製品に付いていた CD の `Driver` フォルダーにある `Quixun_AS11Loader.sys` から取り出します。

```bash
bin/ut100b-firmware extract /path/to/CD/ROBRO_Origin/Driver/Quixun_AS11Loader.sys -o asv5211-firmware.bin
bin/ut100b-firmware load asv5211-firmware.bin
```

`recfriio --firmware asv5211-firmware.bin ...` とすると、ファームの無い UT100B しか無いときに送ってから使います。

## 3. 使い方

- 受けられるのは地デジ（`13`〜`62`）と CATV（`C13`〜`C63`）です。
- UT100B の中の ASIE5606 が USB 転送でかける DES は、いつも外します（放送のスクランブルとは別のもの。外したあとも B25 のスクランブルは残ります）。
- `--b25` は内蔵のスロットのカードを使います。外付けのリーダーを使うときは `--pcsc` を付けます。
- ヌルパケットは UT100B の TS フィルターで捨てているので、`--strip` が無くても出ません（C/C++ 版と同じ）。
- ほかのプロセスが使っている UT100B は選びません（USB のインターフェースを取れないため）。
- 環境変数 `RECFRIIO_USB_TRACE=1` で、送る制御転送を全部、標準エラーに書きます。

```bash
# NHK 総合（ch27 の例）を 30 秒、内蔵の B-CAS で外して録る
bin/recfriio --hdp --b25 27 30 nhk.ts
```

## 6. 技術メモ

この節は実装のときに調べた機器の中身の記録です。

### 6.1 ハードウェア構成

Quixun QRS-UT100B は、地上デジタルテレビ放送用の USB チューナーです。  
ハードウェアの構成は次のとおり。  
チップの刻印を UT100B の実機で確かめたものはなく、確度を分けて書く。

| 部分 | 内容 | 確度 | 根拠 |
|---|---|---|---|
| 製品の系統 | SKNET MonsterTV HDUS 系の OEM 品 | 推定 | 価格.com の分解写真の基板に「SKNET」の文字があるという書き込み、付属品・リモコンが同じという報告。USB の流れ（`1738:5211` → ファーム → 起動）も HDUS と同じ |
| USB ブリッジ | ASICEN **ASV5211**（8051 系のマイコン入り） | 確実 | ファームの無い状態の USB ID `1738:5211`、ブートROMへのファーム転送の手順が ASV5211 のもの |
| カードと USB 転送の暗号の IC | ASICEN **ASIE5606**（B 版、`0x09` の値 `0x06`、I2C `0x4a`） | 確実 | `0x09` の応答と、B-CAS の ATR・APDU が通ること |
| チューナー | ソニーのチューナーモジュール **BTD-VK482Z**（8-597-642-00）。中の IC の型番は不明 | 推定 | HDUS の基板写真（ASCII.jp）。UT100B 自身の刻印は見ていない |
| 復調部 | 東芝 **TC9050x / TC9051x 系**（TC90522 の地上波側と同じレジスタの並び）。モジュールの中にあると見られる | 推定（系統は実測） | C/N のレジスタ `0x8b`〜`0x8d` を Linux の tc90522 と同じ式で換算すると、もっともらしい値（受かる局で約 32 dB、空きで 0）。HDUS の写真では東芝のチップがカバーの外に見えない |
| チューナーの IC | ソニー製のシリコンチューナー（型番は不明。2008 年の地デジ用のソニーの IC では CXA3746 があるが、裏付けなし） | 推定 | ASCII.jp の記事の「チューナーはソニー製」。NM120 ではない（NM120 は coax では `0xce`・16 ビットのレジスタ。こちらは `0xc0`・8 ビット） |

チューナーについて実機で分かっていること:
- 復調部の中継（レジスタ `0xfe`）の先の I2C `0xc0` にあり、8 ビットのレジスタ。  
  周波数は 1/64 MHz 単位で `0x14`・`0x15` に書き、`0x11` を 0 → 2 にして選局する。
- 1 バイトだけの書き込みは命令として受け取る（`0xff` はリセット）。  
  読むと状態の 1 バイト（`0xc8`）が続くだけで、レジスタは読み返せない（下の「読むだけで調べた結果」）。

```text
USB (ASV5211, 3275:7020)
 ├── I2C 0x4a: ASIE5606（B-CAS の内蔵スロット、USB 転送の DES）
 └── I2C 0x20: 復調部 ──[0xfe]──▶ 0xc0: チューナー
```

各レジスタの名前と、意味の分かっていないものは `recfriior5/Hdp.cpp`（タグ `cpp-final`）の先頭にまとめてある。

#### チューナー・復調部を読むだけで調べた結果（2026-11-11）

- 復調部（`0x20`）は全レジスタを読める（`0x02`）。  
  初期化で書いた値がそのまま読め、読み方が正しいことは確かめた。  
  型番を示すレジスタは見つかっていない。
- チューナー（`0xc0`）は、**1 バイトだけの書き込みを命令として受け取る**（初期化で送る `0xff` はリセット）。  
  「読む位置」のつもりで 1 バイトを送ると、受信が止まる（その次の受信の初期化で元に戻る）。
- 中継を開いて読むだけ（`[0xfe, 0xc1]` のあとリクエスト `0x19`）なら受信に影響はなく、何バイト読んでも `0xc8` が続く（状態を返すだけの形）。  
  レジスタを読み返す手段は見つかっていない。

### 6.2 制御の手順

#### ファームの起動

UT100B は通電直後は ASICEN のコールドブート状態（VID: `1738`, PID: `5211`）で認識されます。  
ファームウェア（16 KB）を転送することで、ウォーム状態の `VidzMedia Quixun HDTV`（VID: `3275`, PID: `7020`）に再列挙されます。

##### ファームウェアの入手（付属 CD から）
ファームウェアは付属 CD の `Quixun_AS11Loader.sys`（Windows 用ローダー）の `.data` に、次の形で格納されています。

- 16 KB のファームウェアが 2 つ。  
  各バイトに 1 を加えたうえで AES-128-ECB で暗号化されている。
- 各ファームウェアの 8 バイト前に、起動アドレス（2 バイト、リトルエンディアン）がある。
- 1 つ目がローダーの転送する主のファームウェア、2 つ目は古い版。  
  どちらを転送するかはローダー内の判定で決まる（判定の内容は未解析）。

| `.sys` の版 | 主のファームウェア | 起動アドレス | 備考 |
|---|---|---|---|
| ROBRO Origin 1.08.11.17 | `1f70eb59…` | `0x5399` | PLEX の Linux ドライバーのファームウェア（`b45d5102…`）と 1 バイト（`0x2874`）だけ異なる |
| ROBRO Origin+（forNetbook）1.09.02.19 | `50d406d5…` | `0x53e4` | 別の版（約 8 KB 異なる） |
| （両方の 2 つ目） | `d134890d…` | `0x515f` | PLEX の Windows ローダーにも含まれる古い版 |

`0x2874` の違いは、ポート P1 に書く値のマスク（PLEX `0xF3`、Quixun `0xB3`）で、Quixun 版は P1 の bit 6 を 0 にする。  
bit 6 の接続先は未確認。

```bash
# 取り出しと転送
ut100b-firmware extract /path/to/CD/ROBRO_Origin/Driver/Quixun_AS11Loader.sys -o asv5211-firmware.bin
ut100b-firmware load asv5211-firmware.bin
```

2026-11-11 に、表の主のファームウェア 2 つと PLEX のファームウェアを、それぞれ抜き差しのあとに `tools/ut100b-firmware.py load` で転送して確かめた。  
3 つとも `3275:7020` として出直し、内蔵 B-CAS（`--b25`）で ch19 を 60 秒受けて、TS の誤り・欠けはなく、全パケットのスクランブルが外れた（約 64〜66 万パケット、C/N 約 31〜32 dB）。  
受信の結果に、ファームウェアの違いによる差は見られなかった。

#### ASV5211 の命令（PLEX の Linux ドライバーのライブラリから、2026-11-11）

PLEX の `PX-SERIES_ver.1.0_Linux_Driver`（UT100B が使っているのと同じ ASV5211 のファーム）に入っている `libPlexLib_*.a` は関数名が残っており、ASV5211 の命令の意味がそのまま読める。

| 命令 | PLEX の関数 | 備考 |
|---|---|---|
| `0x00` / `0x01` | GetIRData / SetIRMode | リモコン |
| `0x02` / `0x03` | ReadI2CData / WriteI2CData | 1 レジスタの読み書き |
| `0x04` / `0x05` / `0x09` | ChannelFilter の読み書き / ResetChannel | TS フィルター |
| `0x06` / `0x07` | DSC（受信の開始・停止） | |
| `0x08` / `0x10` / `0x11` | GPIO / GPIOEx の書き込み / GPIOEx の読み出し | |
| `0x0a` | GetDevHighSpeed | USB が高速かの問い合わせ（設定ではない） |
| `0x0c` | GetCusInfo | 基板の情報（58 バイト） |
| `0x0d` / `0x0e` / `0x14` / `0x19` | I2C の溜め・送り / 止めない書き込み / 読み出し | |
| `0x12` / `0x13` | RstEncChip / WriteEncReg | 暗号の IC（UT100B では使っていない） |
| `0x17` / `0x18` | ReadSysCtrlData / WriteSysCtrlData | recfriio の `0x17` はアドレス 2 から 2 バイト読むだけ |
| `0x1a` | GetDevRanKey | 守られた書き込みの使い捨ての値 |

復調部（TC90522 の地上波側）について:
- `0x1c`: PLEX は選局のときに読んで bit 4・5 を立て、少し待って bit 4 を落とす。  
  元の recfriio は `0x9d` を読んだ値（いつも 0）から `0x1c` を作っていて、初期化の表で立てた bit 1 を消していた（`0x28`・`0x38`）。  
  `0x1c` を読んで書き戻す形（`0x2a`・`0x3a`）に直した。  
  9 チャンネルで両方を受け比べ、C/N・誤り・欠けに違いは無かった（2026-11-11）。
- `0x1e`: PLEX は周波数（約 261 MHz の上下）で bit 4・5 を変える。  
  出力の線の設定と見られる。  
  `0x1f` は意味不明。
- `0x9d`: PLEX は BER・SNR を測るときに最初に読む状態のレジスタ。

GPIO の `0x11` は ASIE5606 のリセットで、PLEX の基板・coax と同じ。  
`0xd4`・`0xd5`・`0x08` は基板ごとの配線で、PLEX の基板とは違うので分からない。

#### USB 転送の暗号（ASIE5606、2026-11-11 からの調べ）

UT100B の TS は、復調器から ASIE5606 を通ってブリッジ（ASV5211）に届くとき、ASIE5606 で DES がかかる。  
ソフト（`recfriior5/AsieStreamCipher.cpp`、Go 版は `internal/asie5606/stream_cipher.go`）で元に戻している。

- **放送のスクランブル（ARIB STD-B25）とは別のもの。**  
  この DES は、基板の中の IC どうしの転送にかかる暗号で、放送波にかかっているものではない。  
  外したあとの TS は、放送のスクランブル（MULTI2）がかかったままの普通の TS になる。  
  放送のスクランブルを外すのは `--b25` のときだけで（`arib25/`、Go 版は `internal/b25`）、ECM とワーク鍵の処理は B-CAS カードが受け持つ。  
  以前はこの処理も「スクランブル外し」（`AsieDescrambler`、`descramble.go`）と呼んでいたが、B25 と紛らわしいので名前を変えた（2026-11-15）。
- **止める設定は見つからなかった。**  
  ASIE5606 のレジスタ `0x05` は bit 7 が出力のスイッチで、0 にすると何も出てこない。  
  bit 4 を立てると同期が崩れる。  
  ほかのビット（`0x81`〜`0x8f`、`0xa0`、`0xc0`、`0xe0` など）は、どれも DES が残った。  
  coax が PLEX の同じ版（revision 0x03 = `0x09` の値 `0x06`）で使う `0x20` は、UT100B では出力が止まる。
- **鍵は 0x10〜0x1f で決まる。**  
  普通の書き込みは効かないが、coax と同じ「守られた書き込み」（リクエスト `0x1a` で使い捨ての値をもらい、`0x1c` で書く）なら効く。  
  全部 0 を守られた書き込みで書くと今までどおりに復号でき、coax が PX-W3U3 V2 で書く 16 バイトを書くと復号できなくなった。
- **方式の正体:** 4 バイトのヘッダーはそのまま。  
  残りの 184 バイトに 8 バイト周期の値 `00 00 B1 F2 00 04 F2 04` を XOR したうえで、先頭の 128 バイトを DES 鍵 `bc8c73e90e683123`、残りの 56 バイトを DES 鍵 `ec158001807f8080` で ECB 復号する（鍵 0x10〜0x1f が全部 0 のとき）。  
  `decrypt.c` の鍵の表 `key4allZero` は、この 2 つの鍵の DES の鍵スケジュールそのものだった。  
  標準の DES で復号した結果が、`decrypt.c` の出力とパケット単位で一致することを、実機の受信（約 2.8 万パケット）で確かめた。
- **鍵 `0x10`〜`0x1f` からの導出式（2026-11-15）。**  
  PLEX の `libPlexLib_W3U3.a`（`DTV_5606B2_KeyTransfer1` / `DTV_5606B2_KeyTransfer2`）と UT100B 付属の `Quixun_HDTV_N_BDA.sys`（`0x180fe`〜`0x185ee`）に同じ導出関数があり、16 バイトのシードから 14 バイトの中間値 `a0[0..13]` を作って 8 バイトの XOR（whitening）と 2 つの DES 鍵を組み立てている。  
  - 全部 `0x00` のとき: whitening = `00 00 B1 F2 00 04 F2 04`、先頭鍵 = `bc8c73e90e683123`、末尾鍵 = `ec158001807f8080`。  
  - coax（`px3`）が書く 16 バイト（`00 00 08 00 00 01 c0 04 00 00 c0 a6 00 00 01 00`）のとき: whitening に使われるニブルがすべて 0 になり（whitening = `00 00 00 00 00 00 00 00`）、先頭鍵 = `0cac70e00c6830a0`、末尾鍵 = `ac049084800480c0` になる（実機でもこの 2 鍵・whitening なしで 100% 復号できることを確認済み）。つまり `px3` の 16 バイトは whitening（XOR）を 0 にする値であり、DES 自体を恒等変換にするものではない（DES は 16 段 Feistel 暗号のため恒等鍵は存在しない）。
- **なぜ `px3` は平文で、UT100B は `0x05 = 0x80`（DES 必須）なのか（2026-11-15）。**  
  `DTV_EnableEncryptionChipTSOutput` では、復調器設定バイトの bit 3 に応じて `0x05` の bit 5（`0x20`、バイパス出力ピン）を立て、DES 有効フラグが 1 のときだけ bit 7（`0x80`、DES パイプライン出力）を立てる。  
  PLEX 基板では DES 有効フラグを使わず `0x05 = 0x20` でバイパス側のピンから平文 TS を受け取るが、`Quixun_HDTV_N_BDA.sys`（`0x1a5c8`）は無条件で `or al, 0x80` して `0x05 = 0x80` を書き、常にホスト側のソフト（`DTV_Software_process_5606B2`）で DES 復号している。UT100B の基板配線が bit 7 側の出力にしかつながっていないため、ハードウェアのレジスタ設定だけで DES を省くことはできない。
- **普通の書き込みも要る（2026-11-12）。**  
  0x10〜0x1f に普通の書き込み（I2C）で 0 を書かないと、TS が 1 バイトも出てこない。  
  この書き込みで鍵は変わらない。  
  coax の UT100B 対応で、この書き込みを省いたら受信できず、戻したら受信できた。
- **PLEX のファームでも外れない（2026-11-12）。**  
  PLEX のファーム（b45d5102）を入れても、守られた書き込みのあと `0x05` が `0x20` なら出力が止まり、`0x80` 系なら DES が残った。  
  ブリッジのファームが外しているのではなく、基板が ASIE5606 のどの出力をつないでいるかの違いと考えている。
- 調べるのに使った `RECFRIIO_USB_TRACE=1`（制御転送を全部記録する）は残してある。
- `decrypt.c` は `AsieDescrambler.cpp`（今の `AsieStreamCipher.cpp`）に置き換えた。  
  DES の S 箱・置換は規格（FIPS 46-3）の値をそのまま書き、速さのための表と鍵スケジュールは、上の 2 つの鍵から起動時に組み立てる。  
  `make -C recfriior5 test` で、実機のヌルパケットと、置き換える前の `decrypt.c` の出力を答えに照合できる。

### 6.3 B-CAS（内蔵スロット）

外付けカードリーダー（SCR3310 等）を一切使わず、本体前面の内蔵カードスロットから B-CAS カードを直接制御できます。

`recfriio --hdp --b25` は、この内蔵スロットで復号する（`--pcsc` を付けると外付けのリーダー）。
- `recfriior5/AsieCardReader.cpp` が ASIE5606 のレジスタの窓を通してカードと T=1 でやり取りし（ビットを逆にしたブロック、LRC、続きのある答えの受け取り）、arib25 の `B_CAS_CARD_TRANSPORT` として渡す。  
  arib25 の `b_cas_card.c` は、PC/SC の代わりにこの口を使えるようにした（B-CAS の命令の組み立てと応答の読み取りは元のまま）。
- 手順は coax（`internal/coaxd/smartcard/asie5606`）で調べられたものに従った。
- 実機での確認（ch19）: 20 秒で全 223,885 パケットが復号され、欠けなし。  
  ffmpeg で映像（MPEG-2 1440×1080）と音声（AAC）がデコードできた。
- 1 回の APDU に 150〜250 ms ほどかかる（送り出しに 100 ms、答えを 50 ms ごとに見回る）。  
  ECM の処理はメインのスレッドで行うが、受信は別のスレッドとリングバッファ（20 秒分）で続くので、欠けにはならない。

#### 通信仕様
- **アクセス方法**: ASV5211 経由の USB ベンダーリクエスト
  - Read: `0x02`, `wValue = (reg << 8) | saddr`
  - Write: `0x03`, `wValue = (reg << 8) | saddr`, `wIndex = val`
  - スマートカードコントローラのスレーブアドレス: `saddr = 0x4a`
- **ATR 取得シーケンス**:
  - レジスタ `0x00 = 0x80` → `0x00` → `0x04 = 0x00` で初期化
  - レジスタ `0x00 = 0x08` (Power ON) → `0x04 = 0x80` → `0x00 = 0x09` (Reset)
  - レジスタ `0x03`/`0x39` で受信長取得後、`0x40` 以降から 13 バイトの ATR をビット反転（LSB-first）して取得
  - 取得される標準 B-CAS ATR: `3B F0 12 00 FF 91 81 B1 7C 45 1F 03 99`
- **APDU 送受信**:
  - T=1 プロトコル準拠でコマンド送信後、カード ID（`90 30 00 00 00`）等を取得可能

（recfriio には内蔵 B-CAS リーダーを試す `tools/probe_bcas.c` がある。この Go 版には持ってきていない）
