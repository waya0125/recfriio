# Quixun QRS-UT100B (ASICEN ASV5211 + ASIE5606) 動作仕様 & 検証レポート

## 1. 概要
Quixun QRS-UT100B は、地上デジタルテレビ放送用の USB チューナーです。
内部的には以下のチップセットで構成されています：
- **USB ブリッジ / コントローラ**: ASICEN ASV5211
- **スマートカードコントローラ (内蔵 B-CAS スロット)**: ASICEN ASIE5606
- **復調部**: Toshiba TC90522 の地上波側、またはその互換品（I2C `0x20`）。C/N のレジスタ（`0x8b`〜`0x8d`）を Linux の tc90522 ドライバーと同じ式で換算すると、もっともらしい値（受かる局で約 32 dB、空きチャンネルで 0）になることで確かめた。
- **チューナー**: 型番は未確認。復調部の中継（レジスタ `0xfe`）の先の I2C `0xc0` にあり、8 ビットのレジスタで、周波数を 1/64 MHz 単位で `0x14`・`0x15` に書く。Newport Media NM120（coax では `0xce`、16 ビットのレジスタ）とは別物。
- 各レジスタの名前と、分かっていないものは `recfriior5/Hdp.cpp` の先頭にまとめてある。

本リポジトリでは、現代の Linux 環境において QRS-UT100B での高品質 TS 受信および内蔵 B-CAS スロットの直接制御を実証・実現しています。

## 2. デバイスの認識とファームウェア展開
UT100B は通電直後は ASICEN のコールドブート状態（VID: `1738`, PID: `5211`）で認識されます。
ファームウェア（16 KB）を転送することで、ウォーム状態の `VidzMedia Quixun HDTV`（VID: `3275`, PID: `7020`）に再列挙されます。

### ファームウェアの入手（付属 CD から）
ファームウェアは付属 CD の `Quixun_AS11Loader.sys`（Windows 用ローダー）の `.data` に、次の形で格納されています。

- 16 KB のファームウェアが 2 つ。各バイトに 1 を加えたうえで AES-128-ECB で暗号化されている。
- 各ファームウェアの 8 バイト前に、起動アドレス（2 バイト、リトルエンディアン）がある。
- 1 つ目がローダーの転送する主のファームウェア、2 つ目は古い版。どちらを転送するかはローダー内の判定で決まる（判定の内容は未解析）。

| `.sys` の版 | 主のファームウェア | 起動アドレス | 備考 |
|---|---|---|---|
| ROBRO Origin 1.08.11.17 | `1f70eb59…` | `0x5399` | PLEX の Linux ドライバーのファームウェア（`b45d5102…`）と 1 バイト（`0x2874`）だけ異なる |
| ROBRO Origin+（forNetbook）1.09.02.19 | `50d406d5…` | `0x53e4` | 別の版（約 8 KB 異なる） |
| （両方の 2 つ目） | `d134890d…` | `0x515f` | PLEX の Windows ローダーにも含まれる古い版 |

`0x2874` の違いは、ポート P1 に書く値のマスク（PLEX `0xF3`、Quixun `0xB3`）で、Quixun 版は P1 の bit 6 を 0 にする。bit 6 の接続先は未確認。

```bash
# 取り出しと転送（tools/ut100b-firmware.py を呼ぶ）
./firmware/load_firmware.sh /path/to/CD/ROBRO_Origin/Driver/Quixun_AS11Loader.sys
```

これまでの動作確認（受信・内蔵 B-CAS）は、PLEX のファームウェアで行ったもの。Quixun 自身のファームウェアでの確認はまだ行っていない。

## 3. 内蔵 B-CAS スロットの制御 (ASICEN ASIE5606)
外付けカードリーダー（SCR3310 等）を一切使わず、本体前面の内蔵カードスロットから B-CAS カードを直接制御できます。

### 通信仕様
- **アクセス方法**: ASV5211 経由の USB ベンダーリクエスト
  - Read: `0x02`, `wValue = (reg << 8) | saddr`
  - Write: `0x03`, `wValue = (reg << 8) | saddr`, `wIndex = val`
  - スマートカードコントローラのスレーブアドレス: `saddr = 0x4a`
- **ATR 取得シーケンス**:
  - レジスタ `0x00 = 0x80` → `0x00` → `0x04 = 0x00` で初期化
  - レジスタ `0x00 = 0x08` (Power ON) → `0x04 = 0x80` → `0x00 = 0x09` (Reset)
  - レジスタ `0x03`/`0x39` で受信長取得後、`0x40` 以降から 13 バイトの ATR をビット反転（LSB-first）して取得
  - 取得される標準 B-CAS ATR: `3B F0 12 00 FF 91 81 B1 7C 45 1F 03 99`
- **APDU 送受信**:
  - T=1 プロトコル準拠でコマンド送信後、カード ID（`90 30 00 00 00`）等を取得可能

```bash
# 内蔵 B-CAS リーダーのテストツール
gcc -O2 tools/probe_bcas.c -o tools/probe_bcas
sudo ./tools/probe_bcas
```

## 4. 3 チューナー同時録画品質比較結果
PT3、torne（CECH-ZD1 J）、QRS-UT100B を同一タイミング・同一チャンネル（NHK総合 19ch / 30秒間）で同時受信したパケット品質評価結果です。

```text

 📡 3-Tuner Simultaneous Recording Quality Comparison
================================================================================
Tuner          Size       Bitrate    Duration   SyncErr   TEI Err   CC Drop   Gaps   Judge
--------------------------------------------------------------------------------
PT3            63.1 MB    17.3 Mbps  29.2s      0         0         0         0      ⭕ EXCELLENT
torne          61.0 MB    17.3 Mbps  28.2s      0         0         0         0      ⭕ EXCELLENT
QRS-UT100B     58.5 MB    15.5 Mbps  30.2s      0         0         0         0      ⭕ EXCELLENT
```

- **SyncErr (同期エラー)**: 0
- **TEI Err (RFエラー)**: 0
- **CC Drop (パケット欠落)**: 0
- **Gaps (タイムスタンプ途切れ)**: 0

QRS-UT100B は、PT3 や torne と並び **完全に欠落・エラーのない最高品質（⭕ EXCELLENT）** での同時受信を達成しています。

## TS のスクランブル（2026-11-11 の調べ）
UT100B の TS は、ASIE5606 を通るときにスクランブルがかかり、ソフト（`recfriior5/AsieDescrambler.cpp`、以前は `decrypt.c`）で元に戻している。

- **止める設定は見つからなかった。** ASIE5606 のレジスタ `0x05` は bit 7 が出力のスイッチで、0 にすると何も出てこない。bit 4 を立てると同期が崩れる。ほかのビット（`0x81`〜`0x8f`、`0xa0`、`0xc0`、`0xe0` など）は、どれもスクランブルが残った。coax が PLEX の同じ版（revision 0x03 = `0x09` の値 `0x06`）で使う `0x20` は、UT100B では出力が止まる。
- **鍵は 0x10〜0x1f で決まる。** 普通の書き込みは効かないが、coax と同じ「守られた書き込み」（リクエスト `0x1a` で使い捨ての値をもらい、`0x1c` で書く）なら効く。全部 0 を守られた書き込みで書くと今までどおりに復号でき、coax が PX-W3U3 V2 で書く 16 バイトを書くと復号できなくなった。
- **方式の正体:** 4 バイトのヘッダーはそのまま。残りの 184 バイトに 8 バイト周期の値 `00 00 B1 F2 00 04 F2 04` を XOR したうえで、先頭の 128 バイトを DES 鍵 `bc8c73e90e683123`、残りの 56 バイトを DES 鍵 `ec158001807f8080` で ECB 復号する（鍵 0x10〜0x1f が全部 0 のとき）。`decrypt.c` の鍵の表 `key4allZero` は、この 2 つの鍵の DES の鍵スケジュールそのものだった。標準の DES で復号した結果が、`decrypt.c` の出力とパケット単位で一致することを、実機の受信（約 2.8 万パケット）で確かめた。
- 鍵 0x10〜0x1f の値から、この 2 つの DES 鍵がどう作られるかは分かっていない。
- 調べるのに使った `RECFRIIO_USB_TRACE=1`（制御転送を全部記録する）は残してある。
- `decrypt.c` は `AsieDescrambler.cpp` に置き換えた。DES の S 箱・置換は規格（FIPS 46-3）の値をそのまま書き、速さのための表と鍵スケジュールは、上の 2 つの鍵から起動時に組み立てる。`make -C recfriior5 test` で、実機のヌルパケットと、置き換える前の `decrypt.c` の出力を答えに照合できる。
